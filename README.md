## Project Overview

SudoersEMC is an **independently implemented** Minecraft Forge 1.20.1 mod. It scans the items and recipes registered on a server, computes EMC for items that **ProjectE has not priced yet**, and persists the results in its own data files; when ProjectE is installed, those values are injected through official extension points.

The mod does not modify ProjectE's source code and does not depend on any non-public API. All injection happens through ProjectE's official mapping extension point.

### Core Principles

| Principle                                          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Manual values are never overwritten by default** | `config/ProjectE/custom_emc.json` is read-only by default, and manual values are skipped during injection as well. Only when both `overflow.overwriteScope = entire_custom_emc` and `overflow.allowProjectEFileRewrite = true` are enabled does the mod perform a controlled rewrite of entries in that file that strictly exceed the threshold (backup first, atomic replacement, unknown fields preserved).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Attribution is traceable**                       | Every generated value records its source (recipe / tag / rarity / tier / fallback), recipe ID, ownership, NBT variant hash (if any) and timestamp.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Computation is explainable**                     | For plain entries generated by SudoersEMC that have no NBT variant, `/sudoemc explain <item>` shows the source, recipe, ownership and up to 5 alternative costs (the costs of other valid recipes in the same solve round); entries with NBT variants are not supported yet, and ProjectE-native values and manual values are only reported separately when no generated record exists.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Safety first**                                   | Large price drops in generated candidate values are written to `config/sudoersemc/quarantined_drops.json` in non-dry-run mode and wait for approval; since Phase 26, `/sudoemc approve` writes quarantined values into the generated store by default (source `APPROVED`, `owned=true`) and best-effort triggers a ProjectE remap; when `[safety] approveAppliesImmediately=false` it degrades to an audit mode that only marks the approval status; manual values, exclusions, values below `fallback.minEmc`, invalid values and an unavailable store are all rejected fail-closed. Generated candidates above the cap are reset into a controlled range; creative-only item protection is enabled by default, and exclusions, fixed values, namespaces and large-drop exemptions are all configurable, while automatic detection by default only covers vanilla command/structure items; when an owned entry is detected as modified externally or by a manual value, ownership is released and the external value is kept. |
| **Phased delivery**                                | Since Phase 27, scanning is driven by a real sharded state machine: collection advances across ticks in batches according to `performance.itemsPerTick` / `adaptiveBatchSizing`, pure solving is submitted to the daemon thread `sudoersemc-solver` by default (`[performance] solveOffThread=true`), while application and persistence stay on the server thread; with `solveOffThread=false` it falls back to same-tick solving. Cancellation tokens are observed at batch boundaries and by `Future.cancel(true)`; on cancellation/failure a partial diagnostic report is written; server shutdown or restart resets the scheduler, so a stale `SOLVING` state cannot cause a permanent `DEFER`.                                                                                                                                                                                                                                                                                                                            |
| **Optional dependency**                            | Without ProjectE installed, the mod loads normally and still scans and persists generated values, but does not inject EMC into ProjectE.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

### Phase 18–27 Capabilities

- **solve → fallback multi-round convergence** — completed in Phase 18. `ScanPipeline` runs up to 4 rounds of "recipe solving → fallback seeding"; it converges early when a round produces neither new solved values nor new fallback values.
- **Configurable creative-item protection** — completed in Phase 18. `safety.creativeItemExclusions`, `safety.creativeItemSpecialValues` and `safety.creativeNamespaces` are parsed by `CreativeItemProtection.parseSettings(...)` and wired into pricing exclusions; invalid entries are skipped with a summarized warning.
- **Empty-NBT and default-damage normalization** — completed in Phase 19/20. Empty `CompoundTag`s in recipe outputs (including the `{}` serialized form) are treated as no NBT; tags that only contain the default `{Damage:0}` no longer produce pseudo-variants.
- **Exclusion rules cover the recipe path** — completed in Phase 19. `ScanPipeline.isExcludedFromPricing(...)` is used for both recipe candidates and fallback candidates, so items excluded by tier rules or creative-item protection cannot re-enter the store through the recipe path.
- **Stale owned-entry cleanup** — completed in Phase 19. `ScanPipeline.retireStaleOwnedEntries(...)` removes owned entries that are neither in this round's candidates nor in protected existing values; dry runs or empty snapshots skip it.
- **Quarantined large drops and approval** — completed in Phase 21, extended in Phase 26. In non-dry-run mode every quarantine is written to `quarantined_drops.json` (one record per item, at most 5000 records); `/sudoemc approve <item>` writes the proposed value into `GeneratedEntryStore` by default (source `APPROVED`, `owned=true`) and best-effort requests a ProjectE remap; with `safety.approveAppliesImmediately=false` it only marks the approval status and persists it, without changing EMC or triggering a rescan.
- **Alternative costs and schema v2** — completed in Phase 21. `GeneratedEmcEntry.alternativeCosts` records the costs of other valid recipes in the same solve round; `generated_entries.json` is upgraded from schema v1 to v2 (new `alternatives` array), can still read v1 files but only writes v2; `/sudoemc explain` shows up to 5 alternative costs.
- **Diagnostic report counters and failure details** — completed in Phase 22. `last_report.txt` gains a recipe-scan block that prints total/usable/unsupported/invalid/failed counts and up to 10 failed-recipe details (anything beyond that shows only the remaining total); `PipelineResult.extraCounters` also carries solve rounds, quarantine/retirement counts and the dry-run flag.
- **Scan duration and peak heap sampling** — completed in Phase 22. `ScanManager` samples duration and heap memory at every tick boundary; the report prints total scan time, tick sample count, tick max/average/P95 duration (nearest-rank) as well as peak heap memory and instantaneous heap memory at report time.
- **Partial reports on cancellation/failure** — completed in Phase 22. `ScanManager.AbortListener` notifies the pipeline on cancellation or failure, and `ScanPipeline.writeCancelledReport` / `writeFailedReport` write a partial report marked with `partialReport=1`, `scanCancelled`/`scanFailed` and `scanAborts`.
- **Five-channel incremental fingerprint and startup skip** — completed in Phase 23. `ScanFingerprint` computes sorted SHA-256 truncated digests for items (registry id + rarity, entries de-duplicated), recipes (full content digest), tags (union of item tags), configuration (whitelist of pricing-relevant config) and baselines (ProjectE manual values/tags); `ScanStateStore.compare(...)` returns the channels that changed. At server startup, when "a cache already exists and `alwaysRescan` is not enabled", the current fingerprint is computed and compared, and the scan is skipped when everything matches; a fingerprint computation failure degrades to requiring a scan. `/sudoemc rescan-all` requests a scan directly and is not affected by that skip logic.
- **Cooperative cancellation** — completed in Phase 23. The `ScanCancellation` token is shared by `ScanManager` and `ScanPipeline`; checkpoints exist in item/recipe scanning, NBT variant generation, existing-value reads and the solve/apply loop. On cancellation the scan fingerprint is not updated, stale-entry cleanup and the `custom_emc.json` rewrite are skipped; already staged entries may remain, and the report is written with `scanCancelled` / `partialReport` markers. Dev-server scans take <1s, so live cancellation was not triggered; that path is covered by unit tests.
- **Bounded LRU solve cache** — completed in Phase 23. `RecipeSolver` uses an access-ordered LRU with a default capacity of 8192, keyed by recipe content, evaluation strategy, evaluator registry and input-value snapshot; `ScanPipeline` holds a single `RecipeSolver` instance and reuses it across solve rounds. The report gains `solverCacheHits` / `solverCacheMisses` counters.
- **Recipe selection strategy** — completed in Phase 23. A new `[recipe] selectionStrategy` supports `lowest_cost` (default, ties broken by recipe id), `prefer_simple` (on equal cost, prefers recipes with fewer inputs/outputs/container remainders that are not catalysts, then by id) and `stable_id` (on equal cost, by recipe id). Every strategy uses cost as the primary sort key; invalid values fall back to `lowest_cost` with a single warning.
- **Large-drop protection exemptions** — completed in Phase 24. New `safety.dropProtectionExemptNamespaces` / `safety.dropProtectionExemptItems` keys are wired into `LargeDropProtection.Settings` and `Sudoersemc.createDropProtection()`; they skip large-drop quarantine by namespace (path ignored) or by exact item id, and invalid entries are skipped and summarized in a single warning.
- **Creative-item auto-detection** — completed in Phase 24. New `safety.autoDetectCreativeOnlyItems` (default `true`), `safety.creativeOnlyItemPatterns` (by default only matches vanilla command/structure items) and `safety.autoDetectCreativeOnlyNamespaces` (empty by default); the existing explicit exclusions, fixed values and `creativeNamespaces` rules stay unchanged, and auto-detection only matches the configured regexes/namespaces, so it never implicitly affects ordinary modded items.
- **OwnershipManager external-modification detection** — completed in Phase 24. New `safety.preserveExternallyModifiedValues` (default `true`); before applying, it compares the persisted value of an owned entry with the value observed from the backend in this round and also detects ProjectE manual values, releasing ownership and keeping the external value on a hit, which blocks this round's automated overwrite; the report gains `ownershipExternalModifications` / `ownershipReleasedEntries`.
- **Recipe scan completeness** — completed in Phase 24. `RecipeScanner` distinguishes shaped/shapeless (the report gains `shapedRecipes` / `shapelessRecipes`), supports non-3x3 crafting through `canCraftInDimensions` and the actual width×height, and reads container remainders (`recipe.scanContainerRemainders`, default `true`); `StandardRecipeEvaluator` credits container remainders against the cost when `recipe.creditContainerRemainders` (default `true`) is enabled, and optionally splits multiple outputs per unit through `recipe.priceSecondaryOutputs` (default `false`); with secondary-output pricing disabled, the whole net cost is attributed to the primary output only, avoiding double counting.
- **Config schema migration wired into Forge TOML** — completed in Phase 25. A new root-level `schemaVersion` (legacy default `1`, the current build supports `2`); `Sudoersemc` migrates the on-disk TOML directly before `SudoersemcConfig.register()`, which is the only moment raw content can be preserved before Forge rewrites the file from its spec; `ConfigTomlMigration` edits a temporary file, writes a timestamped `.bak` backup and performs an atomic replacement, refuses to migrate newer versions and keeps the original file for invalid versions. The migration entry point inside `ModConfigEvent` serves as a reload/fallback path and is idempotent.
- **ProjectE-Integration external baselines** — completed in Phase 25. `fallback.useProjectEIntegrationBaselines` (default `true`) reads the positive integer entries of `values.before` from the datapack `pe_custom_conversions` when the `projecteintegration` mod is loaded and a ProjectE provider is available; `#tag` keys, broken entries and broken files are skipped. Baselines only enter the fallback chain as `EXTERNAL_BASELINE` candidates and still go through exclusions, manual values, `fallback.minEmc`, large-drop protection and overflow protection.
- **`diagnostic.debugLogging` rate-limited logging** — completed in Phase 25. The key takes effect on a runtime rebuild; when disabled, hot paths perform a single volatile read and never build messages, and when enabled they use a fixed-window limit of at most 20 messages per second per category, with `DebugLog.summary()` summarizing `total/emitted/suppressed`.
- **ResolverRegistry production wiring** — completed in Phase 25. `Sudoersemc.resolverRegistry()` exposes a process-level registry where third-party mods can register NBT material resolvers; resolution runs in registration order, the first resolver returning a value greater than 0 wins, and a resolver exception only logs a warning and continues with the next one. The registry survives config rebuilds, and its class-name fingerprint participates in the baseline channel, so adding/removing a resolver triggers a rescan.
- **approve auto-application** — completed in Phase 26. `ApprovedDropApplier` runs safety checks in a fixed order: already-approved records are not applied twice, an unavailable store is rejected, audit mode is rejected, the value to apply must be greater than 0 and not below `fallback.minEmc`, ProjectE manual values fail closed (including a missing/throwing predicate), exclusion rules fail closed (including a missing/throwing service); once everything passes, an entry with `PriceSource.APPROVED` is written and a remap is requested best-effort.
- **True sharded collection** — completed in Phase 27. `ItemScanner.scanBatch` / `RecipeScanner.scanBatch` page deterministically over sorted registry ids; `ScanCollector` advances incrementally across ticks in the order "items → recipes → variant observations → variant generation → existing EMC", and `ScanManager` calls `step` every tick during `COLLECTING_SNAPSHOT` within the `BatchProcessor` budget. `performance.itemsPerTick` / `adaptiveBatchSizing` now really control collection batches.
- **Worker-thread pure solving and apply split** — completed in Phase 27. `ScanPipeline.solveOnly` only does ownership separation, seed construction, multi-round solving and candidate selection, without writing the store, reports or state; `SolveWorker` performs the pure computation on the single-threaded daemon thread `sudoersemc-solver`, while the server thread only polls the `Future` and is responsible for collection, application and persistence. With `solveOffThread=false` it falls back to same-tick solving.
- **Shutdown reset preventing a hang** — completed in Phase 27. `resetScanManagerForShutdown` cancels and resets `ScanManager` on both the shutdown and restart paths, preventing a stale `SOLVING` state from leaving the next runtime rebuild permanently `DEFER`red.

### Not Yet Implemented / Currently Inactive

The following capabilities are **not implemented yet**, **currently inactive**, or subject to known limitations worth noting:

- **Forge rewrites the TOML (known limitation)** — Forge rewrites configuration files from its spec after loading, so unknown keys and hand-written comments may be dropped by Forge on the first load; SudoersEMC's pre-parse migration guarantees that the pre-migration content is fully backed up as a timestamped `.bak`, but it cannot prevent Forge's subsequent normalization.
- **Live Goety verification** — not done yet. Phase 20 changed required-field read failures to fail-closed (skipping the whole recipe), but the reflection path can only be fully verified in a real Goety environment; there is no live-server record yet.
- **Representative modpack performance measurement** — not done yet. Phase 22 only recorded scan duration, tick samples and peak heap on the dev server, without measuring a representative modpack or comparing against a baseline.
- **Live-environment verification of NBT variants** — Phase 17 wired the path and has unit tests, and Phases 19/20 only added empty-NBT and default `{Damage:0}` normalization; vanilla recipes produce no NBT output, so it has not been verified in a real environment, and `/sudoemc explain` does not cover entries with variants either.

### Optional Integrations

- **ProjectE-Integration** — does not interfere with this mod. Existing EMC visible through `IEMCProxy` is treated as "already priced" and is not overwritten by this mod; since Phase 25, `fallback.useProjectEIntegrationBaselines` (default `true`) reads the positive integer entries of `values.before` from the datapack `pe_custom_conversions` when both the `projecteintegration` mod and a ProjectE provider are available, feeding them into the fallback chain as `EXTERNAL_BASELINE` candidates; when the mod or the provider is missing, it degrades to an empty baseline.
- **Goety** — code-level support exists for Goety 2.5.60.6 `goety:ritual`: only the `goety:craft` type participates in item pricing, while summoning, conversion, enchanting, teleporting and locating rituals are skipped. The reflection parsing path has not been verified on a live Goety install; when parsing fails it degrades to "unavailable" and skips the ritual.

## Installation

1. Install Minecraft Forge 1.20.1 (47.x).
2. Put `sudoersemc-<version>.jar` into the `mods/` directory.
3. If the generated EMC should take effect in game, install ProjectE 1.0.1 as well.
4. Start the server or client. The configuration file is generated on first launch.

## Configuration

Configuration file: `config/sudoersemc-common.toml`

> The keys below are generated into the configuration file by Forge, and every key listed in this document is read by production code. Phase 16 wired hot reload: `ModConfigEvent` rebuilds the runtime components, and `/sudoemc reload` triggers the same rebuild path with the currently loaded configuration values. While a scan is running, the rebuild is deferred until the scan ends; when cross-field validation fails, the rebuild is rejected and the previous valid components are kept. Since Phase 25 the root-level `schemaVersion` is wired in: the on-disk TOML is migrated at mod load time before Forge parses it, and the pre-migration content is backed up as a timestamped `.bak`.

### Auto Scan

`general.enabled = true` enables the automatic scan at startup; `general.alwaysRescan = true` forces a rescan on every startup; when neither applies, startup enumerates the current item registry/recipes and computes the five-channel input fingerprint: a scan is triggered only when "it has never scanned", "the generated entries are empty", or the fingerprint differs from the value saved in `scan_state.json`, otherwise the cache is reused. A fingerprint computation failure degrades to requiring a scan. `/sudoemc rescan-all` requests a scan directly and is not affected by that skip decision. Auto scanning is independent of whether ProjectE is installed. These two keys are only read at server startup, so changing them requires a server restart to change the auto-scan decision; the other scan-related keys take effect on `/sudoemc reload` or a Forge config reload through component rebuilds.

```toml
schemaVersion = 1   # root-level; do not edit manually (the current build supports 2)

[general]
enabled = true
alwaysRescan = false

[performance]
itemsPerTick = 100                 # Phase 27; collection batch budget per tick
adaptiveBatchSizing = true         # Phase 27; adapts from the previous batch's duration (1–8x)
solveOffThread = true              # Phase 27; pure solving is submitted to the daemon thread sudoersemc-solver

[recipe]
solveRecipes = true
maxRecipePasses = 20
allowRecipeValueIncrease = false
selectionStrategy = "lowest_cost"   # lowest_cost | prefer_simple | stable_id
```

`recipe.selectionStrategy` decides how to choose between several recipes with the same cost for one item: `lowest_cost` (default, ties broken by recipe id), `prefer_simple` (on equal cost, prefers recipes with fewer inputs/outputs/container remainders that are not catalysts, then by id) and `stable_id` (on equal cost, by recipe id). Every strategy uses cost as the primary sort key and never accepts a recipe above the lowest feasible cost; invalid values fall back to `lowest_cost` and log a single warning. The key participates in the five-channel config fingerprint, so changing it triggers an incremental scan on the next server startup.

`[recipe]` keys added in Phase 24: `scanContainerRemainders` (default `true`) reads container remainders when scanning crafting recipes; `creditContainerRemainders` (default `true`) credits the known EMC of returned containers when evaluating cost, preventing buckets/bottles and similar items from being double priced; `priceSecondaryOutputs` (default `false`), when enabled, splits the net cost across all outputs per unit so every output receives the same per-unit value, and when disabled the whole net cost is attributed to the primary output only.

`[safety]` keys added in Phase 24: `dropProtectionExemptNamespaces` / `dropProtectionExemptItems` skip large-drop quarantine by namespace and by exact item id respectively (invalid entries are skipped and summarized in a warning); `autoDetectCreativeOnlyItems` (default `true`) enables automatic detection, `creativeOnlyItemPatterns` by default only matches vanilla command/structure items, `autoDetectCreativeOnlyNamespaces` is empty by default, and auto-detection never implicitly affects ordinary modded items; the explicit exclusions, fixed values and `creativeNamespaces` rules keep their original semantics. `preserveExternallyModifiedValues` (default `true`) detects before applying whether an owned entry was modified externally or by a ProjectE manual value, and on a hit releases ownership and keeps the external value, blocking this round's automated overwrite. Real modded creative items still require explicit configuration.

Configuration keys added/updated in Phase 25: the root-level `schemaVersion` defaults to `1` (legacy), the current build supports `2`, and it must not be edited manually; the mod migrates old files to the current version before Forge parses them and backs up the original file. `fallback.useProjectEIntegrationBaselines` (default `true`) is actually effective: only when ProjectE-Integration is installed and a ProjectE provider is available does it read `values.before` from the `pe_custom_conversions` datapack as an external baseline, otherwise it returns an empty baseline. `diagnostic.debugLogging` (default `false`) is actually effective: when enabled it emits debug logs per category with at most 20 messages per second per category, suppressed entries are summarized at the end of the scan; when disabled, hot paths perform a single volatile read.

Configuration keys added in Phase 26/27: `[safety] approveAppliesImmediately` (default `true`) controls whether `/sudoemc approve` writes the quarantined value into the generated store immediately after approval; setting it to `false` degrades to audit mode, which only marks the approval status without writing EMC or triggering a remap. `[performance] solveOffThread` (default `true`) submits pure solving to the daemon thread `sudoersemc-solver`; setting it to `false` solves synchronously on the server thread, matching the behavior before Phase 26. `performance.itemsPerTick` and `performance.adaptiveBatchSizing` really control collection batches since Phase 27: the former is the base budget per tick (the adaptive upper bound is 8x), the latter grows, shrinks or keeps the batch based on the previous batch's duration.

### Overflow Protection

When a **generated candidate value strictly exceeds** `threshold`, SudoersEMC replaces it with a weighted random value in the `100..999000` range (`[resetMin, resetMax]`):

- the range is split into `bucketCount` buckets, with bucket weights biased toward low values along a quadratic curve;
- each bucket's weight is hard-clamped to `[1, weightCap]`, so the highest value always remains reachable while no single bucket can monopolize it with a probability close to 100%;
- a non-zero `randomSeed` makes results reproducible, which helps testing; `0` means re-randomize on every startup;
- values already inside the reset range are not randomized again (idempotent).

ProjectE-native values and manual values in `custom_emc.json` never enter this candidate path; the manual file can only be modified through the controlled `ENTIRE_CUSTOM_EMC` rewrite described below.

### Rewrite Scope

| Value                  | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `owned_only` (default) | Only resets candidate entries generated by SudoersEMC itself that are about to be written.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `entire_custom_emc`    | Controlled rewrite of ProjectE's `custom_emc.json`, **requires `allowProjectEFileRewrite` to be enabled as well**. When enabled, entries in the file strictly above `threshold` are reset into `[resetMin, resetMax]`; a `custom_emc.json.<timestamp>.bak` backup is created before writing, the write uses a temporary file plus atomic replacement, and unknown fields and key order are preserved. If the file is missing, corrupt or structurally invalid it is left untouched. Rewrite results are recorded in `overflow_resets.json` (`scope = ENTIRE_CUSTOM_EMC`). Enabling either switch alone never rewrites the file; a scope conflict logs a warning on load or reload. |

The scope and switches are read on a runtime rebuild; they take effect after `/sudoemc reload` or a Forge config reload.

## Config Validation & Migration

### Actual Behavior

- **Single-field ranges** are validated by Forge's `defineInRange` at load time, and out-of-range values are corrected into the allowed range. Covered keys are `performance.itemsPerTick`, `recipe.maxRecipePasses`, `fallback.minEmc`, `overflow.threshold`, `overflow.resetMin`, `overflow.resetMax`, `overflow.bucketCount`, `overflow.weightCap`, `safety.maxAllowedDropRatio` and `nbt.maxNbtVariantsPerItem`.
- **Runtime cross-field validation** has been wired since Phase 16: `ConfigValidator.validateCurrent()` runs `validateCrossField(...)` on config load/reload events and on `/sudoemc reload`. `overflow.threshold <= resetMax`, `overflow.resetMin > resetMax`, `overflow.resetMin < 1`, `bucketCount < 1` and `weightCap < 1` reject the rebuild and keep the previous valid components; `overwriteScope = entire_custom_emc` with `allowProjectEFileRewrite = false` only logs a warning and does not rewrite the file.
- An invalid `overflow.overwriteScope` falls back to `owned_only` at parse time with a warning and does not reject the rebuild.
- An invalid `recipe.selectionStrategy` falls back to `lowest_cost` at parse time with a single warning and does not reject the rebuild; the key participates in the config fingerprint, so changing it triggers an incremental scan on the next server startup.
- The list keys added in Phase 24, `safety.dropProtectionExemptNamespaces` / `dropProtectionExemptItems` / `creativeOnlyItemPatterns` / `autoDetectCreativeOnlyNamespaces`, are validated entry by entry by `ConfigValidator`; invalid entries are only skipped with a summarized warning and do not reject the rebuild.
- The Forge range of `safety.maxAllowedDropRatio` is `[0.0, 1.0]`; if it is set to `0.0`, the `LargeDropProtection.Settings` constructor fails and the scan pipeline falls back to the default `0.5` (rather than rejecting the whole configuration).
- The Forge range of `nbt.maxNbtVariantsPerItem` is `[1, Integer.MAX_VALUE]`; values above `1000` are not rejected at runtime, but `VariantScanner` truncates the actual scan count with the hard cap `1000`.
- If the overflow settings fail to construct at startup, the scan pipeline falls back to the built-in defaults; runtime rebuilds are all-or-nothing: the old components are replaced only after all new components have been built successfully.
- `/sudoemc reload` rebuilds the runtime components from the currently loaded configuration values; while a scan is running it returns "will take effect after the scan ends", and when validation fails it returns "kept the previous valid configuration". It does not actively re-read the TOML from disk; after editing the configuration file directly, Forge detects the change and fires `ModConfigEvent.Reloading`, which goes through the same rebuild path.
- `ConfigValidator` and `ConfigWatcher` are wired into the production config load flow; `ConfigMigrations` is wired in through `ConfigTomlMigration`: the on-disk TOML is migrated at mod load time before Forge parses it, and the entry point inside `ModConfigEvent` serves as the reload/fallback path.

### Migration (wired in Phase 25)

Forge 1.20.1 has no public "pre-parse" config hook. Phase 25 migrates the on-disk `config/sudoersemc-common.toml` directly before `SudoersemcConfig.register()`, which is the only moment raw content can be preserved before Forge rewrites the file from its spec; the migration entry point inside `ModConfigEvent.Loading/Reloading` serves as the reload/fallback path, and already migrated files return `NO_OP`.

- **Current version**: `schemaVersion = 2`, matching `ConfigMigrations.SCHEMA_VERSION`; the root-level key defaults to legacy `1`.
- **v1 → v2**: adds `999999` when `overflow.threshold` is missing, and `owned_only` when `overflow.overwriteScope` is missing; existing values are left unchanged.
- **v2 → v2**: no changes and no notices.
- **Higher than v2**: migration is refused and the original file is kept (`REFUSED_NEWER`); the mod never overwrites a future version's configuration.
- **Unknown version (`<= 0`)**: `schemaVersion = 0` is treated as legacy 1 and migrated; a missing key is likewise treated as legacy 1.
- **Invalid version**: negative numbers, non-numeric strings, booleans/arrays/decimals and other invalid types keep the original file and log a warning (`FAILED_RETAINED`).
- **Write strategy**: known keys are first modified on a temporary file; on success the original file is backed up as `sudoersemc-common.toml.<timestamp>.bak` and then replaced atomically; when the filesystem does not support atomic moves it degrades to a plain replacement. Any failure keeps the original file and cleans up the temporary file.
- Migration only reads and writes `schemaVersion`, `overflow.threshold` and `overflow.overwriteScope`; it never rewrites the whole configuration.

> **Known limitation:** Forge rewrites the TOML from its spec after loading, so unknown keys and hand-written comments may be dropped by Forge on the first load. The pre-parse migration guarantees that the pre-migration content is fully backed up as a timestamped `.bak`, but it cannot prevent Forge's subsequent normalization. In addition, a `schemaVersion` above `Integer.MAX_VALUE` is refused by the pre-parse migration, but Forge may still correct the out-of-range value to the default `1` afterwards.

## How It Works

At server startup the mod first migrates the on-disk TOML before Forge parses it; if auto scanning is enabled and `alwaysRescan` is not set, the mod then computes the five-channel input fingerprint and compares it with `scan_state.json`; when they match, this round's scan is skipped, and when they differ or the computation fails, the flow below runs. `/sudoemc rescan-all` always requests a scan directly.

1. **Query** — uses `IEMCProxy` to determine whether an item already has EMC; existing values (other than SudoersEMC's own entries) are treated as already priced.
2. **Compute** — derives candidate values from recipes, tags, rarity, tier and fallback rules; tags and rarity come from the actual item snapshot (`getTags()` / `getRarity()`). When an item has several recipes, multi-round solving (including cycle detection) takes the lowest valid deterministic cost, and equal costs are resolved by `[recipe] selectionStrategy`; since Phase 23 `RecipeSolver` uses a bounded LRU evaluation cache and checks the cancellation token inside recipe loops. Since Phase 24 `RecipeScanner` distinguishes shaped/shapeless and supports non-3x3 grids through the actual width×height, and container remainders are stored in the recipe snapshot; `StandardRecipeEvaluator` credits returned container value when `recipe.creditContainerRemainders` is enabled, and splits the net cost per unit across all outputs when `recipe.priceSecondaryOutputs` is enabled. Since Phase 17, NBT observed in recipe outputs produces variant snapshots with a `variantHash` that enter the same solve flow; since Phase 19/20, empty NBT and tags containing only the default `{Damage:0}` are handled as plain items. Since Phase 25, the fallback chain can use ProjectE-Integration external baselines or third-party NBT resolver `EXTERNAL_BASELINE` candidates before TAG/RARITY, and they likewise pass through exclusions, manual values, minimum EMC and overflow threshold checks first. Vanilla recipes produce no NBT output, so this has not been verified in a real environment. Since Phase 27 solving only reads immutable snapshots and performs the pure computation on the daemon thread `sudoersemc-solver` by default (`solveOffThread=true`), while collection, application and persistence stay on the server thread; with `solveOffThread=false` it falls back to synchronous solving on the server thread.
3. **Safety** — applies large-drop protection to generated candidate values (drops above the threshold are written to a quarantine record and wait for approval, with per-namespace/per-item exemptions), creative-only item protection (supporting explicit configuration and automatic detection, where automatic detection by default only matches vanilla command/structure items) and overflow protection; before applying, it detects whether an owned entry was modified externally or by a ProjectE manual value, and on a hit releases ownership and keeps the external value, preventing this round's overwrite; when both switches are enabled it also performs the controlled `custom_emc.json` file rewrite.
4. **Persist** — writes the results into `generated_entries.json` and marks ownership (`owned=true`); later scans first clear the mod's own entries and re-solve, and clean up stale owned entries that no longer participate in pricing, so recipe or tag changes are reflected in the generated values. Entries with a Phase 24 external-modification hit are kept with `owned=false` and their external value, and are not overwritten in this round. A cancelled scan does not update the `scan_state.json` fingerprint and skips stale-entry cleanup and the `custom_emc.json` rewrite.
5. **Write** — through ProjectE's official `@EMCMapper` extension point with `priority = -1000`, injects its own entries via `setValueBefore` when ProjectE recomputes EMC; manual values are skipped.
6. **Recompute** — triggers a resource reload on the server thread, and ProjectE rebuilds its EMC mapping.
7. **Diagnostics** — the scan pipeline collects recipe scan statistics, solve rounds, solve cache hits/misses, quarantine/retirement counts, tick durations and heap samples into `PipelineResult.extraCounters`, and writes them to `last_report.txt` after the scan; Phase 24 additionally outputs `shapedRecipes` / `shapelessRecipes`, `multiOutputRecipes` / `containerRemainderRecipes` and `ownershipExternalModifications` / `ownershipReleasedEntries`; Phase 25 additionally outputs `externalBaselineAvailable` / `externalBaselineEntries` / `externalBaselineApplied` and `resolverRegistered` / `resolverApplied` counters. On cancellation or failure, `AbortListener` writes a partial report that keeps the statistics of the collected snapshot and the termination-reason markers.
